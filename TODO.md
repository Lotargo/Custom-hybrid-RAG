# Проект "Распределенный Гибридный RAG-движок": Архитектура и TODO-лист

## 1. Концепция и Архитектурное Видение
Цель: Создание бескомпромиссного, сверхбыстрого и распределенного гибридного RAG-движка (векторный + полнотекстовый поиск), оптимизированного под Linux (C++20/23). Продукт строится с учетом zero-allocation на горячих путях, максимального использования кэша L1/L2 и возможностей ядра ОС.

### Основные компоненты архитектуры:
- **Client Facing:** Кастомный бинарный TCP-протокол (boost.asio / io_uring), FFI интерфейсы (C-API) для интеграции.
- **Query Processing:** Модуль RRF (Reciprocal Rank Fusion) для слияния результатов векторного и BM25 поиска, отсечение по метаданным (Bloom/Roaring Bitmaps).
- **Embedded AI:** Инференс-пул (ONNX/GGML) с привязкой потоков к ядрам процессора, встроенные токенизаторы BPE/WordPiece, Cross-Encoder для Reranking.
- **Index Engines:**
  - Векторный индекс HNSW (lock-free вставка).
  - Лексический индекс (сжатые постинг-списки).
- **Storage Layer:** Tiered Storage. RAM + mmap для индексов (NVMe), madvise-оптимизации. LSM/B-Tree для метаданных. Write-Ahead Log (WAL).
- **Math Core:** SIMD (AVX2/AVX-512) оптимизированные функции расстояний (float32, int8 квантование). Zero-copy.
- **Distributed Layer:** Consistent Hashing, Raft консенсус, Gossip протокол для обнаружения нод. Изоляция через Namespaces.

## 3. Анализ рисков и Предотвращение проблем (Risk Mitigation)

Для создания идеального продукта важно заранее предусмотреть "узкие горлышки" и архитектурные ошибки.

### 3.1 Проблемы многопоточности и Lock Contention
- **Риск:** Глобальные мьютексы (Global Locks) при вставке в HNSW индекс сведут на нет преимущества мощного CPU.
- **Решение:** Использование строгих lock-free структур или fine-grained locks (блокировка на уровне узлов графа/шардов). Применение Thread-Local Storage (TLS) для буферов вычислений.

### 3.2 Сетевой I/O как бутылочное горлышко (Zero-Allocation)
- **Риск:** Аллокации памяти при каждом сетевом запросе вызовут фрагментацию памяти и высокую нагрузку на Garbage Collection ОС/Аллокатор (например, malloc).
- **Решение:** Использовать jemalloc или tcmalloc. В сетевом слое заранее аллоцировать Ring Buffers под TCP пакеты. Использовать `std::string_view` и `std::span` для парсинга пакетов без копирования.

### 3.3 Падения сервера и потеря данных (Durability)
- **Риск:** mmap и отложенная запись (Page Cache) могут привести к коррупции индекса при OOM Killer или аппаратном сбое.
- **Решение:** Использование строгого Write-Ahead Log (WAL) для всех транзакций записи. Использовать `msync()` с флагом `MS_ASYNC` (и периодически `MS_SYNC` в фоне) для HNSW графа. Восстановление HNSW графа из WAL при перезапуске, если файлы повреждены.

### 3.4 Непредсказуемый Latency ML инференса (Tail Latency)
- **Риск:** Переключение контекста (Context Swapping) ОС между тяжелыми потоками нейросетей увеличит p99 latency.
- **Решение:** Thread Affinity (привязка потоков инференса жестко к ядрам, `pthread_setaffinity_np`). Разделение пулов потоков: I/O потоки (сеть) отдельно, Compute потоки (инференс и поиск) отдельно.

### 3.5 Проблема фрагментации индексов (Index Compaction)
- **Риск:** Постоянное добавление и удаление документов приведет к фрагментации Inverted Index и HNSW графа, замедляя поиск и тратя дисковое пространство.
- **Решение:** Архитектура Segment-based хранилища (как в Lucene/Elasticsearch). Индекс пишется неизменяемыми сегментами (Immutable Segments). Фоновый процесс (Compaction) прозрачно сливает мелкие сегменты в крупные и очищает удаленные документы без блокировки поиска (MVCC - Multi-Version Concurrency Control).

### 3.6 Сложность тестирования распределенных систем (Split-Brain & Raft)
- **Риск:** При сбоях сети кластер может распасться на две части (Split-Brain), что приведет к конфликтам данных и потере консенсуса.
- **Решение:** Использовать строгие реализации Raft без самодеятельности (доказанные библиотеки или скрупулезный порт). Обязательное создание хаос-тестов (Jepsen-style) — искусственное отбрасывание TCP пакетов, заморозка потоков (`SIGSTOP`/`SIGCONT`) для проверки корректности перевыборов лидера.
